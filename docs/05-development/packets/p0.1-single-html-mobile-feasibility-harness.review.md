## 4. Findings

### F1 -- Production SelectionService is not connected to StudyState

**Severity:** blocking
**Location:** src/app/state.js (APP.createState / emit), src/app/dom.js (emitCtx), test/helpers.js / test/selection.test.js
**Observed:** APP.createState(service) accepts a service argument but never calls service.subscribe(...) or otherwise connects service emissions to state.emit. The production DOM path sends selections with service.emit(ctx). The state only changes through its separate state.emit(context) method. The Node harness then tests state semantics by calling state.emit(...) directly, bypassing the central service-to-state integration.
An independent semantic reproduction of the exact relevant logic produced:

```
{"current":null,"updates":0}
```

after service.emit(verseContext).
This means the production browser path does not establish the behavior the passing state tests appear to demonstrate. The tests exercise the state machinery, but not the actual production selection wiring.
**Expected:** Emitting a verse/word/place through the central SelectionService must update StudyState and the compatible pane views. The automated tests must exercise the same production wiring.
**Required action:** Wire StudyState to the service, for example by subscribing during state construction or through an equivalent single production integration point. Change the acceptance-path tests to emit through SelectionService, not directly through state.emit. Add a regression test proving service.emit(...) changes state.currentContext() and notifies the correct pane(s). Re-run the browser checks because criteria 4-8 depend on this path.

### F3 -- Two criterion-11 failure fixtures do not demonstrate a non-zero verification exit

**Severity:** blocking
**Location:** test/failure.test.js -- broken selection propagation is caught by the probe and a pinned pane that follows is caught by the probe
**Observed:** The tests for external JS, external CSS, fetched fixture, and missing artifact each spawn lint.js and assert:

The packet's claim that all six injected breaks are asserted to fail closed with a non-zero exit is therefore not true for these two cases.

**Required action:** Put the propagation/pin verification behind a CLI or child-process verification path, introduce the sabotage in that child process, and assert its exit status is non-zero, matching the first four cases. Keep a positive control proving the unsabotaged path exits zero.

### F4 -- buildId omits artifact-affecting inputs while documentation calls it a hash of the build inputs

**Severity:** advisory
**Location:** scripts/build.js -- INPUT_FILES, buildIdFor, assemble; build-metadata comments/documentation
**Observed:** The build defines:

```
const INPUT_FILES = ['package.json', 'scripts/build.js'].concat(JS_FILES);
```

But assemble() additionally reads:

```
src/index.html
src/ui/styles.css
src/ui/icons.svg
```

Those files affect the bytes of dist/manna.html, but they do not participate in buildIdFor(inputs).
Therefore, for example, changing a CSS declaration or changing the HTML shell can change the release artifact while leaving buildId unchanged.
sourceFiles also reports only the narrower INPUT_FILES count even though the artifact has additional source inputs.
The build comment states that the Build ID is a hash of relative paths plus contents for the build inputs, and the packet describes it as deterministic build metadata. That description is incomplete/misleading while artifact-affecting inputs are excluded.
**Expected:** Build metadata must be truthful and deterministic. If buildId is defined as a hash of build inputs, every artifact-affecting input must participate.
**Required action:** Include src/index.html, src/ui/styles.css, and src/ui/icons.svg, plus any other artifact-affecting inputs, in the Build ID input set. Alternatively, formally redefine and rename the field and correct all documentation if the specification permits that narrower meaning. Add regression coverage showing that changing each artifact source changes buildId.
Under this repository's review protocol, an advisory is still a must-fix finding and therefore prevents PASS.

### F5 -- Diagnostics does not show the actual artifact SHA-256 required by criterion 12

**Severity:** blocking
**Location:** scripts/build.js (sha256 versus sha256Embedded), src/app/dom.js Diagnostics build card, implementation packet build-metadata sections
**Observed:** The build computes two different hashes.
First, before inserting the embedded value, it computes:

```
const shaEmbedded = crypto
  .createHash('sha256')
  .update(html, 'utf8')
  .digest('hex');
```

That html contains the placeholder value in the digest field.
The placeholder is then replaced with shaEmbedded, changing the file bytes.
After that, the code computes:

```
const sha = crypto
  .createHash('sha256')
  .update(html, 'utf8')
  .digest('hex');
```

This second value is the SHA-256 of the actual final manna.html bytes.
The final-byte sha256 is written into BUILD-MANIFEST.json and manna.html.sha256.
However, MANNA_META contains only sha256Embedded, and Diagnostics renders:

```
ARTIFACT SHA-256
<sha256Embedded>
```

The UI note then acknowledges that this value was computed over the artifact with its digest field blanked.
So Diagnostics does not display the same SHA-256 that identifies the actual final artifact bytes.
**Expected:** Criterion 12 says:

```
Build metadata (app version, build ID, artifact SHA-256) is visible in Diagnostics without exposing local paths.
```

The review protocol does not permit reinterpreting a verbatim acceptance criterion to match what was implemented.
**Required action:** Resolve the requirement explicitly before re-review. If the intended field is a normalized/embedded digest because a literal self-hash is impossible, clarify/amend the authoritative requirement through the project's decision process and label the value accurately. Otherwise implement a mechanism that makes the actual final artifact SHA-256 available in Diagnostics. Do not label sha256Embedded as ARTIFACT SHA-256 while the build records a different hash as the actual final artifact SHA-256.
