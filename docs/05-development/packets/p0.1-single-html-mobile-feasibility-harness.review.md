central service:


```js
const service = SEL.createService();
const state = APP.createState(service);
```

```js
service.emit(H.verseCtx(16));
```

and asserts that:

* `state.currentContext()` moved to verse 16;
* Commentary received verse 16;
* Cross References received verse 16;
* Word Study did not incorrectly follow the verse event.

That regression passed in exact-head CI.

The original defect is therefore closed.

## 5. Findings

### R2-F1 -- Criterion 12 still requires the true artifact SHA-256 to be visible in Diagnostics

**Severity:** blocking

**Location:**

```text
docs/05-development/ROADMAP.md -- P0.1 criterion 12
src/app/dom.js -- Diagnostics BUILD card
scripts/build.js -- sha256 / sha256Embedded
docs/05-development/packets/p0.1-single-html-mobile-feasibility-harness.md
```

**Observed:**

The original review found that Diagnostics labelled `sha256Embedded` as the
artifact SHA-256 even though `scripts/build.js` separately calculated a
different hash over the final artifact bytes.

The remediation corrected the misleading label.

Diagnostics now renders:

```text
SHA-256 (DIGEST FIELD BLANKED)
<sha256Embedded>
```

and the explanatory note says:

```text
Computed over the artifact with its digest field blanked — a file cannot
contain its own SHA-256. The artifact's true SHA-256 is recorded in
BUILD-MANIFEST.json and manna.html.sha256.
```

This is truthful.

However, the current roadmap acceptance criterion still says:

> Build metadata (app version, build ID, artifact SHA-256) is visible in
> Diagnostics without exposing local paths.

At the reviewed head the values are:

```text
true final artifact SHA-256:
600f7465613d9d235cd53ef5dc81216d90f7c26856af32afc404e5c42cf0d97f

blanked-field digest shown in Diagnostics:
e55400611aa977b16e770cfab9bb2fae6cd1157dbf24db01ddf853d9d47474bc
```

These are deliberately different.

The true artifact SHA-256 is therefore not visible in Diagnostics.

Putting the value in `BUILD-MANIFEST.json` or `manna.html.sha256` does not
satisfy a criterion requiring it to be visible in Diagnostics.

The current packet describes F5 as addressed because the field was relabelled,
but the relabelling only fixed the false claim. It did not satisfy the
acceptance criterion.

**Expected:**

The implementation and authoritative requirement must agree.

One of the following must become true:

1. Diagnostics actually displays the value that `scripts/build.js` calls
   `manifest.sha256`, meaning the SHA-256 of the final `manna.html` bytes; or
2. the authoritative acceptance criterion is deliberately amended through the
   project's decision process so it requires the normalized/blanked-field
   digest rather than the impossible literal self-hash.

The review protocol explicitly prohibits reinterpreting an acceptance criterion
to fit what was built.

**Required action:**

Resolve the requirement explicitly.

If the normalized embedded digest is the intended design:

* record that decision in the appropriate authoritative design/governance
  location;
* amend criterion 12;
* keep the accurate `SHA-256 (DIGEST FIELD BLANKED)` label;
* update the packet to cite the amended criterion.

If the existing criterion is retained:

* implement a truthful way for Diagnostics to expose the true final artifact
  SHA-256.

Do not mark prior F5 closed solely because the incorrect label was removed.

### R2-F3 -- Criterion 9's required “by tap” behavior is not demonstrated

**Severity:** blocking

**Location:**

```text
docs/05-development/ROADMAP.md -- criterion 9
test/browser.test.js
docs/05-development/packets/p0.1-single-html-mobile-feasibility-harness.md
```

**Observed:**

Criterion 9 says:

> All required interactions work at phone width by tap, with no hover-only
> affordance and no horizontal overflow.

The current browser test makes important progress.

For its phone run it configures:

```text
width: 360
height: 800
mobile: true
touch emulation enabled
maxTouchPoints: 5
Android Chrome user-agent
```

It then verifies visible button geometry and horizontal clipping.

That catches the bottom-navigation overlap defect.

However, it does not exercise the required application interactions through
touch input.

For navigation it executes JavaScript in the page:

```js
document.querySelector('[data-nav="reader"]').click()
```

That invokes DOM click behavior directly.

The reachability test then reads element rectangles.

It does not send touchscreen coordinates or touch/pointer input through the
browser.

As a result, this test proves:

* the phone layout is rendered;
* touch capability can be emulated;
* buttons are geometrically reachable;
* horizontal clipping is checked;
* fixed navigation does not overlap visible controls.

It does not prove the criterion's explicit:

```text
work ... by tap
```

requirement.

The packet's current self-assessment independently acknowledges that
physical-device tap behavior remains a human step.

**Expected:**

The required P0.1 phone workflow must be exercised through an actual touch/tap
input path at phone width.

This should cover at least:

1. primary navigation;
2. Reader navigation;
3. selecting a verse;
4. observing Commentary update;
5. observing Cross References update;
6. tapping a tagged word;
7. observing Word Study update and Strong's entry;
8. tapping a tagged place;
9. observing Atlas update;
10. opening the mobile study drawer/pane navigation;
11. pinning Commentary;
12. selecting another verse while pinned;
13. confirming Commentary remains held and visibly pinned/stale;
14. unpinning;
15. confirming Commentary resumes following.

The test must also verify:

```text
document.documentElement.scrollWidth <= window.innerWidth
```

or equivalent throughout the phone flow.

**Required action:**

Perform one of:

* a physical-phone tap walkthrough; or
* an automated browser/device test that sends genuine touch/pointer events
  through the browser's input protocol rather than invoking DOM `.click()`
  directly.

Record the interaction results.

A touch-enabled viewport plus direct JavaScript `.click()` is not sufficient for
a criterion explicitly requiring tap behavior.
