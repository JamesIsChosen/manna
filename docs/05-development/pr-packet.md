# The PR packet

Every unit of work ships as a **PR packet**: the branch, plus a document that
lets someone who was not involved verify the work **without trusting the person
or agent who did it**.

That framing drives everything below. A packet that says "I tested it and it
works" is worthless for independent review. A packet that says "here is the
command, here is its output, here is what I could not verify" is useful.

## Where it lives

`docs/05-development/packets/<item-id>-<slug>.md`, matching the branch name.

Per-item paths, never a single rotating `PR-PACKET.md`: packets are the
permanent audit trail, and a shared path causes a merge conflict on every
stacked branch.

Its contents also go in the PR description.

## Required sections

### 1. Summary
Which roadmap item, what changed, three sentences or fewer. Link the item.

### 2. Scope
What is **in** this PR and what is deliberately **not**. Anything touched
outside the roadmap item, and why.

### 3. How to verify
The exact commands a reviewer runs, **with the output you got**. Not a
description -- the commands and their output.

```
$ npm ci && npm run lint
<paste>

$ npm test
<paste>

$ npm run build
<paste>
```

### 4. Acceptance criteria
Copied **verbatim from the roadmap item**. For each: how it is satisfied, and
which test proves it.

| Criterion | How satisfied | Test |
|---|---|---|

An unmet criterion means the item is not done. Say so rather than reinterpreting
the criterion to fit what was built.

### 5. Test evidence
- New tests, and what each proves
- Negative tests: what you made fail deliberately, and how it failed
- Anything you could not test, and why

### 6. Assumptions made
Every decision the spec did not settle. This is where a reviewer finds the real
risk. A decision that should have been the spec's belongs back with the spec,
not buried here.

### 7. What to scrutinise
Where are you least confident? What is subtle? What would you look at if you
were reviewing someone else's version of this?

Answering "nothing, it's straightforward" is almost always wrong and reads as such.

### 8. Self-assessment
- What might be wrong with this?
- What did you not do that arguably should have been done?
- Known limitations shipping with this change
- Follow-up work this creates, with roadmap items filed

### 9. Docs updated
Which docs changed. Whether any now contradict the code or the spec.

## Conditional sections

Required when the project has the surface. **A conditional section that does not
apply is written as `N/A -- <why>`, never omitted silently.** An absent section
is indistinguishable from a forgotten one.

### 10. Security impact
When the change touches auth, secrets, crypto, user data, network boundaries, or
permissions.

- What does an attacker gain if this implementation is wrong?
- Any new external host, and what it learns about the user
- Any new message/IPC type, and proof it cannot carry sensitive material

If the honest answer to the first question is "I'm not certain", write that. It
is the most useful sentence in the packet.

### 11. Device / platform matrix
When the change is browser- or UI-facing.

| Platform | Result | Notes |
|---|---|---|

Untested platforms are marked untested. Never inferred from a similar one.

### 12. Bundle / size impact
When the project has a size budget. Before / after / delta.

## Standards of evidence

**Show, don't assert.** "Build verified" is an assertion. Two hashes pasted from
two builds is evidence.

**Independent sources only.** Test data generated by the implementation being
tested proves nothing. Cite the upstream spec, a reference implementation, or a
second tool.

**Negative results count.** "I tried X to break it and it held" is evidence.
"I tried X and it broke, here is the fix" is better evidence.

**Absence of evidence is reportable.** A gap you flagged is a manageable risk. A
gap you hid is a latent failure.

## Before you request review

Read your own diff as a hostile stranger using the reviewer's checklist, and fix
anything you would flag. Any finding of any severity is a FAIL, so there is no
upside to leaving a rough edge and considerable upside to flagging your own
uncertainties.
